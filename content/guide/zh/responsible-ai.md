# 可信与负责任 AI

模型即使平均准确率很高，在特定人群、语言或环境中，以及执行工具操作时，仍可能出现严重错误。负责任的研究需要说明系统的用途、受影响的人，以及现有证据仍无法消除的不确定性。没有一个分数能单独证明系统可信。

把本章作为查阅入口：选择与论文或项目相关的问题，理解定义，再检查证据。第一个项目不必完成所有类型的评估。[研究方法](research-methods.md)介绍比较与不确定性，[数据集和评测](datasets.md)介绍数据与指标。

<a id="scope-context"></a>

## 从人和使用情境开始

画出从数据收集、输出到后续行动的过程。谁提供信息、使用结果、承担错误的后果，又有谁能够质疑结果？研究原型和自动作出决策的系统，需要的证据与监督不同。

自愿性框架 [NIST AI RMF](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.100-1.pdf)通过 Govern、Map、Measure、Manage 四个部分梳理这些问题。它帮助分析风险，不是模型认证。

例如，能够核对原文的研究者使用翻译辅助，与无法读懂源语言的读者依赖翻译，承担的风险不同。同样的输出质量可能有不同后果。先明确用途、受影响的人、可能的错误与纠正责任，再选择指标。

<a id="data-documentation"></a>

## 问清数据和标签代表什么

标签可能直接测量目标，也可能只是代理。点击既反映相关性，也受曝光与用户行为影响；历史决策可能延续先前做法。缺失情况和标注分歧也可能随人群变化。

[Datasheets for Datasets](https://arxiv.org/abs/1803.09010)围绕采集、构成、处理、用途与维护提出问题。先问数据涵盖哪些人和对象、标签如何产生、哪些条件未被覆盖。未知信息应明确记录，不能因为数据公开就假定它适合当前任务。

**阅读检查：**高分是否只说明模型很好地预测了记录中的标签，却没有完成真实目标？来源与划分可继续查[数据审查](datasets.md)。

<a id="fairness"></a>

## 理解公平性指标在比较什么

公平涉及人与系统。统计准则只能刻画其中某个明确方面，需要解释它为何适合当前情境。移除敏感特征，不代表其他特征没有携带相关信息。

| 二分类准则 | 比较对象 |
| --- | --- |
| 人口统计均等 Demographic parity | 各组被预测为正的比例 |
| 机会均等 Equal opportunity | 各组真正例率 |
| 均等化机会 Equalized odds | 各组真正例率与假正例率 |
| 组内校准 Group calibration | 各组预测概率与实际发生频率 |

[Fairlearn](https://fairlearn.org/main/user_guide/assessment/common_fairness_metrics.html)解释定义及其假设。同时检查分母、标签质量、小群体的表现和不确定性。测得差距小，不能单独证明待遇公平。部分准则在特定条件下不能同时满足；[风险评分原始研究](https://arxiv.org/abs/1609.05807)讨论的是明确的不可兼容条件，而非所有公平目标彼此冲突。

**阅读检查：**为何选择这一准则，谁的错误更重要，还有哪些群体或后果没有被考察？需要实现时可查 [MetricFrame](https://fairlearn.org/main/api_reference/generated/fairlearn.metrics.MetricFrame.html)与 [AIF360](https://github.com/Trusted-AI/AIF360)。

<a id="robustness-ood"></a>

## 区分不同的鲁棒性问题

新的医院、相机、语言、时期，图像损坏，以及刻意构造的对抗变化，是不同评估情境。说明什么发生了变化、为什么原标签仍有意义，以及攻击者掌握的信息与预算。

[WILDS](https://wilds.stanford.edu/)研究真实分布变化，[RobustBench](https://robustbench.github.io/)组织明确定义的鲁棒性基准。解释结果前先读任务与威胁模型。在一种条件下表现良好，不能据此推断系统能够可靠应对所有变化。

同时报告绝对性能和下降幅度，并检查受影响的群体与失败类型。一次攻击未成功，只是关于受测攻击的有限证据，不是安全证明。

<a id="calibration"></a>

## 区分置信度、校准与拒答

对于校准良好的二分类预测器，在评估总体中，预测为正类的概率接近 0.8 的样本，应有接近 80% 实际属于正类。这描述一组预测，不保证某个具体答案正确。语言模型口头表示“确定”，也不自动成为校准过的概率。

可靠性图比较预测概率与实际发生频率。[scikit-learn 校准指南](https://scikit-learn.org/stable/modules/calibration.html)解释 Brier score、log loss 为何还反映校准之外的性质；分箱方式与样本数也会影响判断。开发数据上拟合的校准器，应在独立评估数据上检查，分布变化后也要重新考察。

采用拒答机制时，需要权衡覆盖率与保留样本的错误率。二者都应报告，同时说明哪些样本被拒绝、之后如何处理。少回答困难问题可能提高表面准确率，却没有改善这些用户获得的服务。

<a id="interpretability"></a>

## 问清解释能够证明什么

可解释模型结构、特征归因和现实中的因果解释回答不同问题。[InterpretML](https://interpret.ml/docs/ebm.html)介绍加性模型，[SHAP 解释](https://interpret.ml/docs/shap.html)为指定模型输出分配特征贡献；它们都不能单独说明真实干预会产生什么后果。

阅读归因时核对模型、输出尺度、背景数据和相关特征处理。[置换重要性](https://scikit-learn.org/stable/modules/permutation_importance.html)可能给共同携带信息的相关特征分别赋予很低的重要性。好看的热图仍需要明确的定义与验证。

**阅读检查：**主张针对模型计算、人的理解，还是现实中的原因？评估是否对应这个主张？

<a id="privacy-memory"></a>

## 分清记忆、隐私与访问控制

训练数据提取、成员推断，以及检索记录或当前上下文泄露，涉及不同数据流。[训练数据提取研究](https://www.usenix.org/conference/usenixsecurity21/presentation/carlini-extracting)说明记忆为何值得关注；少量提取尝试未成功，不能证明保密。

差分隐私约束一个机制在指定相邻数据集上的输出分布变化。其保证取决于保护单位、隐私参数、具体机制和隐私预算核算。记录级保护不自动等于用户级保护；删除姓名或随意加噪也不构成 DP 保证。重复使用私有数据可能需要组合分析，隐私预算也不会因新建一个核算器（accountant）而重置。可查 [Opacus FAQ](https://opacus.ai/docs/faq)和 [Dwork–Roth 教材](https://www.cis.upenn.edu/~aaroth/Papers/privacybook.pdf)。

训练中的隐私保护不会自动保障应用日志的机密性，也不会赋予读取记录的权限。分别梳理采集、训练、检索、日志与发布。学习时可以使用虚构记录，不必测试他人的私人信息。

<a id="llm-agent-security"></a>

## 理解语言模型与 Agent 的信任边界

外部文本可以包含指令，但检索内容不会因此成为经过授权的命令。模型提出工具调用，也不等于有权执行。画出用户请求、外部来源、模型、工具、数据与执行器，再确定每个边界由谁控制。

[OWASP 提示注入指南](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)与[过度代理权限指南](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)介绍常见失效方式。最小权限、资源检查、参数校验和执行限制属于外围系统，不能仅靠一段提示词实现。

| 问题 | 查看什么证据 |
| --- | --- |
| 外部内容能否改变任务？ | 完整轨迹与越权请求 |
| 工具能否读取另一个用户的资料？ | 资源级权限校验 |
| 建议操作能否超出权限或预算？ | 执行器决定、实际影响、限制与终止 |

区分提出越权请求和实际越权执行。学习时可在受控环境分析模拟工具与虚构数据；除了攻击结果，也报告正常任务失败与错误拒绝。

<a id="human-evaluation"></a>

## 说明人工评估的依据与过程

正确性、有用性、清晰度、偏好和伤害是不同判断。定义评分规范，并给评估者完成任务所需的证据。多数人偏好一个答案，不等于这个答案事实准确。

[人工评价报告研究](https://aclanthology.org/2020.inlg-1.23/)说明定义与程序的重要性。检查输出如何抽样、评估者如何分配、掌握什么语言与知识、是否隐藏系统身份、如何安排呈现顺序，以及平局、缺失和分歧如何记录。正式评估前先试用并修订说明。

同一输出的多次评分不是新的独立样本。不确定性分析应考虑样本和评估者带来的依赖关系。使用 LLM judge 时，用代表性样本对照合适的人类判断，并说明评分规范、版本及其对筛选的影响。

<a id="release-documentation"></a>

## 说明证据覆盖的范围

[Model Cards](https://arxiv.org/abs/1810.03993)与数据说明将预期用途、评估和限制对应到具体版本。写清受测人群与条件、已知失败、访问限制和未测范围。只有“公平”“鲁棒”“隐私”等词，没有定义与证据，读者很难判断含义。

学习项目可以先有简洁的 README 与范围明确的评估说明。持续发布的系统还需要联系入口、维护责任，以及数据、模型、使用人群或权限改变后重新评估的条件。文档帮助审查，不能替代它所描述的评估。

<a id="project-acceptance"></a>

## 把发现转化为决定

把每个关注点串成**检查的条件 → 观察 → 尚存不确定性 → 下一步决定**。区分失败、证据不足、不适用与未测试。

例如，仅在英文问题上测试的原型，可以支持相应的英文研究结果，却不能据此声称多语言可靠。下一步可以缩小主张，也可以针对明确的其他语言人群开展评估。仅用统一的通过阈值作判断，会掩盖这一推理过程。

主要研究选择可参考[决策记录](research-methods.md#experiment-record)整理，再加上与当前问题有关的人、风险、评估条件和未解问题；不必为每个主题重复填写长表。

<a id="learning-resources"></a>

## 选择适合当前阶段的学习路线

从一篇论文或熟悉的项目开始，解释使用情境与数据。再选一个问题，例如群体错误、来源变化、校准或工具权限，简要评议证据支持什么。讨论一项具体改进及检验它所需的证据。

不同资源各有用途：NIST 帮助梳理风险；Fairlearn、AIF360 用于实施具体评估；WILDS、RobustBench 提供明确定义的评估情境；scikit-learn、InterpretML 解释测量方法；Opacus 介绍一种隐私保护方法；OWASP 帮助梳理威胁；Model Cards、Datasheets 帮助完善记录。按当前问题选择资源。
